# M3 框架：HMW 拆解与闭环目标定义（D2 上午 09:00–12:00）

> 对应日程：MVL闭环目标定义、HMW拆解与AI方案方向锁定。
> MAAU 落点：**Workflow（工作流）草案** —— 核心业务链路 / 关键节点 / 分层验证维度；**Intent 回填** —— 闭环目标 / 能力指标 / 验收标准。
> 方法来源：`references/methods/10-hmw.md`、`references/methods/14-insight-four-steps.md`。

## 讨论支架（引导师用）

| 环节 | 时间盒 | 产出 |
|------|--------|------|
| 洞察收敛：裁决昨日反馈，锁定 1 个最关键用户时刻 | 30 min | 问题焦点 |
| HMW 改写三步：用户时刻 → 张力 → 问法 | 40 min | HMW ×1-2 |
| 发散与收敛：Crazy 8s（或组内头脑风暴）→ 聚类 → 机会主题+设计原则 | 60 min | 创意池+原则 |
| 闭环目标定义：触发→完成、能力指标、验收标准 | 50 min | 闭环目标卡 |
| 方案方向锁定：四维投票（用户价值·可行性·数据就绪·规则明确） | 30 min | 优先方向 |

## 引导问题清单

1. HMW：把核心痛点改写成「我们如何能……」？写完删光技术名词再读一遍
   - 鉴别：预设解法的是坏问题；笼统不可操作的是平庸问题；有用户时刻+张力的是好 HMW
2. 这个闭环的核心目标一句话：Agent 自动完成什么事，人从哪解脱出来？（业务结果，不是功能）
3. 闭环从哪里触发、到哪里算完成？（起点终点必须具体）
4. 核心业务链路分几步？每步：谁做（Silicon 执行 / Carbon 复核 / Carbon 决策）、输入什么、输出什么？
5. 哪些节点必须人工确认？为什么（风险/合规/体验）？
6. 能力指标与验收标准：闭环的关键能力用什么数字衡量？怎么判定通过？
7. 设计原则：这个机会主题下，做方案必须遵守哪几条原则？
8. 被放弃的方向是什么、为什么？（必须记录，防止反复回头）

## 提取字段

| 字段 | 说明 | 必填 |
|------|------|------|
| problemFocus | 锁定的最关键用户时刻（谁+何时+被什么卡住） | 是 |
| hmw[] | HMW 问题清单（附改写前的原始痛点） | 是，≥1 条 |
| loopGoal | 闭环核心目标一句话 | 是 |
| loopBoundary | 触发点 / 完成点 | 是 |
| steps[] | 业务链路：步骤 / 执行者(S·C) / 输入 / 输出 / 节点类型 | 是 |
| humanCheckpoints[] | 人工确认节点及理由 | 是 |
| capabilityMetrics[] | 能力指标 / 验收标准 / 验证维度 | 是 |
| designPrinciples[] | 机会主题 + 设计原则 | 尽量 |
| direction | 选定方案方向 + 被放弃方向及原因 | 是 |

## 质量检查清单（及格线）

- [ ] 链路是闭环：有明确触发点和完成点，能走通回到业务结果
- [ ] 每个节点标注执行者类型（Silicon 执行 / Carbon 复核 / Carbon 决策）
- [ ] HMW 不含技术名词、不预设解法
- [ ] 验收标准可判定（是/否能验，而非「体验良好」）
- [ ] 被放弃的方案方向已记录并附原因

## 陷阱（引导时提醒小组）

HMW 写成解决方案 / 创意只有一个思路（强制换对象、换触点、换时机）/ 聚类变站队（按能力簇聚不按人簇聚）/ 投票变人情票（四维各自独立打分）。
