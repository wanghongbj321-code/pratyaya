# 5w-distill：丰田 5W 根因分析提炼

把 Key Points 概览与丰田 5W 思考模型结合，形成经过对齐的、唯一事实源的确认包（`modules/5W-{slug}-v{N}.md`）。完成标准是"经业务方、技术方、管理层各自动用都能成立的根因分析资产"，不是"看起来内容丰富"。

所有 5W 产物必须绑定 instance slug。slug 由主 Agent 提供，必须为 kebab-case，并与 `state.five_whys.{slug}.slug` 一致；本 Skill 不自动生成 `default` slug。

## 定位

**分步提炼流程**：本 skill 是 Pratyaya Canvas Expert 的"5W 提炼与确认包生成"能力。完整的 5W 工作流由主 agent 编排（见 `agents/pratyaya.md`），本 skill 不编排主流程，只在被调用时执行以下两个独立 Stage：

- **Stage 1：Key Points 抽取** — 输入转写，输出 `modules/5W-{slug}-keypoints.md`（讨论地图，30 秒浏览）。
- **Stage 2：原子提炼** — 输入转写 + Key Points + 丰田 5W 框架，输出 `modules/5W-{slug}-v{N}.md`（确认包，唯一事实源）。

调用顺序由主 agent 决定，本 skill 不强制。本 skill 不调用 Canvas 渲染、不执行闸门判定。

## 唯一内容边界

开始任何 Stage 前必须读取：

1. 丰田 5W 框架 `frameworks/5w-five-whys.md`：核心原则、三层面追问、五层追问句式、每层合格检查点、停止准则、对策要求；
2. `references/5w-spec.md`：5W Key Points 与确认包的固定 section 定义、ID 约定、Canvas 锚点映射。

只提取用户实际讨论的内容。框架之外的方法或术语不自动成为必填项、补问项或放行条件；只有用户明确使用时，才按原话记录。

## 引用层级（重要）

**不引用逐字稿段落**。与 GC / HMW 蒸馏一致的立场——头脑风暴的逐字稿不具备段落级权威性：同一人在讨论前后可能表达矛盾立场、口语化试探与跑题占据大量文本、真正的事实来自"确认环节达成的共识"而非某段话。引用应基于：

- **Key Points 内的 section**（如"问题陈述（候选）"）
- **确认包自身的 section**（如"5W 缺口表 G01"）

逐字稿从"证据"降级为"背景材料"，仅作存档，不作引用源。

## 输入与输出

| Stage | 输入 | 输出 |
|---|---|---|
| Stage 1：Key Points 抽取 | 逐字稿（文本或文件路径） | `modules/5W-{slug}-keypoints.md`（第 N 轮） |
| Stage 2：原子提炼 | 逐字稿 + Key Points + 丰田 5W 框架 | `modules/5W-{slug}-v{N}.md`（确认包，唯一事实源） |

Stage 1 与 Stage 2 可独立调用，不强制串联。但 Stage 2 的输入依赖 Stage 1 的 Key Points。

Stage 2 完成后交给主 agent 触发闸门（`5w-gate`），不直接进入 Canvas 渲染。

## Stage 1：Key Points 抽取

**目标**：在 30 秒内让用户了解"这次讨论了什么、问题陈述与因果链覆盖度如何、缺什么"。

**触发**：主 agent 5W 工作流对应步骤，输入为逐字稿（已由主 agent 存档为 `transcripts/5w-{slug}-TXX-raw.md`）。

**输出**：`modules/5W-{slug}-keypoints.md`，结构如下。

### 5W-{slug}-keypoints.md 模板

```markdown
# 5W 根因分析 Key Points（第 X 轮）

> 生成时间：{YYYY-MM-DD HH:MM}
> 画布类型：5W Five Whys（根因分析）画布
> 轮次：第 X 轮
> 数据源：transcripts/5w-{slug}-TXX-raw.md

## 1. 讨论主题

本次讨论覆盖了哪些主题（每个 1-2 句，最多 5 条）：

- **主题 1**：...
- **主题 2**：...

## 2. 问题陈述（候选）

从转写中提取的事实性陈述（附发言来源）：

- 候选陈述 1：...（来源：...）
- 候选陈述 2：...

> 必须是事实而非结论。若原始表达是结论（如"团队混乱"），标注"需改写为可验证事实"。

## 3. 因果链线索（按层组织）

- Why 1（直接原因）：候选答案 1 / 证据线索
- Why 2（直接原因）：候选答案 2 / 证据线索
- Why 3（漏检缺口）：候选答案 3 / 证据线索
- Why 4（漏检缺口）：候选答案 4 / 证据线索
- Why 5（系统缺陷）：候选答案 5 / 证据线索

## 4. 对策与行动线索

- 候选对策 1：...（提及的负责人：...；提及的验证信号：...）

## 5. 覆盖度初判

对照丰田 5W 框架（`frameworks/5w-five-whys.md`），粗略评估覆盖情况：

| 区块 | 状态 | 简评 |
|---|---|---|
| 问题陈述 | 已覆盖 / 部分覆盖 / 未涉及 | ... |
| Why 1（直接原因） | ... | ... |
| Why 2（直接原因） | ... | ... |
| Why 3（漏检缺口） | ... | ... |
| Why 4（漏检缺口） | ... | ... |
| Why 5（系统缺陷） | ... | ... |
| 根本原因 | 已覆盖 / 部分覆盖 / 未涉及 | ... |
| 对策四要素 | ... | ... |

## 6. 用户决策提示

> 基于以上概览，请选择：**提炼** / **补问** / **先看个样子**
```

**约束**：

- 长度控制：每节最多 5 条，供 30 秒快速浏览。
- 不做原子提炼、不写结论登记表、不评估缺口。
- 末尾必须输出用户决策提示。
- 跨轮次覆盖：第 N 轮 Key Points 覆盖第 N-1 轮摘要（同文件覆盖式更新，保留最后一轮）。
- 覆盖度初判必须包含问题陈述 + Why 1-5 各层 + 根本原因 + 对策四要素。

## Stage 2：原子提炼

**目标**：将 Key Points 转化为经过对齐的、唯一事实源的确认包 `5W-{slug}-v{N}.md`。

**触发**：主 agent 5W 工作流对应步骤（用户回复"提炼"后调用）。

**输入**：

- 逐字稿（已存档）
- `modules/5W-{slug}-keypoints.md`（Stage 1 产物）
- `frameworks/5w-five-whys.md`（丰田 5W 框架）

**输出**：`modules/5W-{slug}-v{N}.md`，全 Markdown，结构如下。

### 5W-{slug}-v{N}.md 确认包模板

```markdown
# 5W 根因分析确认包 v{N}

> 画布类型：5W Five Whys（根因分析）画布
> 版本：v{N}（基于第 X 轮 Key Points）
> 状态：{draft / gaps_open / review_ready / confirmed / rendered}
> 生成时间：{ISO 8601 datetime，由 skill 生成时写入}
> 确认人：{待填写}
> 确认人角色（可选）：{待填写}
> 确认时间：{待填写，ISO 8601 datetime}

### 6. 问题陈述

### 7. 因果链（五层，三层面）

| 层 | 层面 | 追问对象 | 答案（因为…） | 证据 | 合格检查点 |
|---|---|---|---|---|---|

| Why 5 | 系统缺陷 | 【原因 4】 | ... | ... | ... |

### 8. 根本原因

| 字段 | 内容 | 来源引用 |

### 9. 对策四要素

| verify（如何验证有效） | ...（信号 / 指标） | ... |

> 此节为 Canvas 渲染中 `5w-countermeasure` / `5w-owner` / `5w-due` / `5w-verify` anchor 的事实源。

### 10. 其他原因分支

### 11. 判别记录（rubric）

| 坏答案（被打回） | 问题类型 | 好答案（采纳） |
|---|---|---|

> 记录工作坊中实际发生的判别对照（打回的坏答案 + 改写后的好答案）。数据源为 Key Points 中的纠偏记录；无实际打回记录时显示"无"。

### 12. 结论登记表

| ID | 结论 | 所属层 | 类型 | 共识状态 |
|---|---|---|---|---|

> 本表只记录"经过讨论产生的结论"；推断不写入此表。

### 13. 缺口表

| ID | 等级 | 所属区 | 状态 | 描述 | 缺失影响 | 最少补问 |
|---|---|---|---|---|---|---|
| 5W-G01 | blocker | Why 3 证据 | open | ... | ... | ... |

> 等级定义：blocker = 使 5W 核心产出（问题陈述 / 因果链 / 根因）无法成立；major = 会显著改变根因分析方向或对策；minor = 不改变核心结论，可后续补齐或明确接受风险。
> 状态定义：
> - `open`：未关闭；Gate 评估时仍按等级计入 PASS/FAIL。
> - `closed`：已解决；可作为关闭依据进入下一轮或当前轮评估。
> - `accepted_risk`：用户/确认人已显式接受风险；属治理元数据，由用户在确认环节写入，不由本 skill 写入。

### 14. 推断表

|---|---|---|---|---|

> 推断不写入结论登记表与固定 Canvas section。
```

## 升版边界

确认包版本受两类写入影响：

| 写入范围 | 是否触发升版 | 是否重跑 Gate | 是否重置授权 |
|---|---|---|---|
| 第 1–16 节业务内容（含问题陈述、因果链、根因、对策、判别记录、结论、缺口、推断、引用）变化 | **是**（vN → vN+1） | **是** | **是**（清空 `gate_recommendation` / `render_authorized` / `confirmation_mode` / `override_audit`） |
| 仅第 17 节"Gate 与用户决策"治理元数据写入（Gate 报告、用户决策、Override 审计） | **否**（保留 vN） | 否（已是当前评估结果） | 否（这是当前版本的授权写入） |

**规则**：

- **业务内容变化**：必须 `version + 1` + `gate_recommendation=pending` + `render_authorized=false` + `confirmation_mode=null` + 清空当前版本 `override_audit`；旧版本确认包归档为 `5W-{slug}-v{N}.md.previous`，旧版第 17 节审计随旧版保留。
- **治理元数据写入**（仅第 17 节）：不触发升版；Gate 报告摘要与用户授权属于当前版本的元数据补充。
- **历史版本审计**不得清空：旧版 `5W-{slug}-v{N}.md.previous` 的第 17 节（包括历史 override 审计）必须完整保留，用于追溯。

## 元数据生成时间字段

- `生成时间`（`5W-{slug}-v{N}.md` 顶部）由本 skill 在 Stage 2 生成确认包时按系统真实时间写入（ISO 8601 datetime）。
- `确认时间`由主 Agent 在用户决策后写入；不得使用 skill 生成时间。
- 禁止在文件名、文档标题、报告标识中编造时间戳。

## 质量红线

1. 不编造、不拔高、不抹平冲突。
2. 问题陈述必须是事实；结论型表达（"团队混乱"）必须改写为可验证事实并标注改写。
3. 每层"因为"答案必须有关键证据（日期 / 记录 / 日志），证据缺失标缺口，不得补写。
4. 禁止个人归因；出现"没注意 / 素质差 / 不重视"类表达必须打回并记录到判别记录（§11）。
5. 推断必须独立登记（§14），不得混入结论或 Canvas section。
6. 不引用逐字稿段落；引用应基于 Key Points / 确认包内的 section。
7. 未完成人工确认前，不视为提炼完成；状态由主 agent 在"确认 vN"后写入。
