# User Journey 画布框架（动态阶段 × 5 行合并结构）

> 画布类型：User Journey（用户旅程）画布
> 理论边界：独立一等公民画布，不影响 MVL M2 `09-user-journey.md`

本文件由 `journey-distill` 在 Stage 1 和 Stage 2 时读取，是 Journey 提炼的唯一内容边界。正式数据契约忠实保留 `canvas-templates/02-用户旅程画布.html` 的 5 行合并结构；不得改成 MVL method09 的七要素。

> **v2.3.2 PATCH**：第 4 / 5 行 key 从 `wait_rework` / `risk` 切换为 `pain_point` / `opportunity`，中文表头从「等待与返工 / 风险节点」切换为「痛点 / 机会」；6a 维度键从 `friction_visible` 切换为 `pain_opportunity_visible`。

## 主表结构

| 行 key | 展示名 | 含义 | 引导问题 |
|---|---|---|---|
| action | 行动 | 用户在这步做了什么 | 这一步用户实际做了什么？用动词短语。 |
| touchpoint_system | 触点与系统 | 和谁 / 什么交互，使用什么系统 / 文档 | 用户和谁或什么交互？用了什么系统、表单或文档？ |
| emotion | 情绪 | 用户感受 | 用户这一步感受如何？高 / 中 / 低，或正向 / 中性 / 负向。 |
| pain_point | 痛点 | 当前阶段的等待、返工、断点或不可控 | 等了多久？有没有返工？为什么返工？哪里最可能出错？ |
| opportunity | 机会 | 当前阶段可转化的潜在改进空间 | 这一步有没有可转化的机会点（不写方案）？ |

## 阶段规则

- 阶段根据实际旅程动态生成，不固定 7 个槽位。
- 最低 3 个有效阶段。
- 单次 Journey 画布只承载一条旅程；多旅程通过多次运行或多个项目产物表达。
- 起点到终点应覆盖到"业务结果产生"，而不是停在"系统处理完"。

## 质量鉴别（正式画布外显）

| 维度 key | 展示名 | 判据 |
|---|---|---|
| user_perspective | 用户视角 | 是否从用户动作和感受出发，而不是组织 / 部门视角 |
| business_outcome | 到达业务结果 | 终点是否到用户拿到结果 / 业务价值产生 |
| pain_opportunity_visible | 痛点与机会可见 | 痛点与机会是否明确标出 |
| no_solution_bias | 未预设方案 | 当前旅程是否没有提前写入 AI / 解决方案判断 |

## 最低结论要求

- 至少 3 个有效阶段。
- 每个有效阶段 5 行字段均有内容或显式标为缺口。
- 至少标出 2 个痛点、1 个机会，或明确说明未发现。
- 质量鉴别四维度必须全部判定。

## 不得自动引入

- 不得把 Journey 主表改为七要素。
- 不得新增第 6 行承载质量鉴别；质量鉴别是正式画布外显治理区块。
- 不得因为离线工作表当前有 5 个槽位而固定正式阶段数量。
- 不得在当前旅程中提前写入解决方案、AI 应用判断或 Future Journey 设计。
- 不得把组织图、部门职责或系统泳道替代为用户旅程。
- 不得写入 MVL、覆盖 MVL M2 或自动同步任何 Journey 结论到 `state.modules.M2`。
